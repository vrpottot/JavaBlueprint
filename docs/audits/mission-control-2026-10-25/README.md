# Mission Control: второй большой прогон JavaScope

Создан новый самостоятельный [монолит MissionControl.java](../../../backend/examples/mission-control/MissionControl.java): **1 566 строк, из них 1 442 непустые**, 85 методов, 11 обычных и четыре компактных конструктора. Рядом [16 JUnit-тестов](../../../backend/examples/mission-control/MissionControlTest.java). Код представляет симуляцию космических миссий с маршрутизацией, зависимостями, ограниченными ресурсами, дедлайнами, журналом событий и телеметрией, а не набор однотипных функций для добора строк.

## Проверка Java

Настоящий JDK 21 с `-Xlint:all -proc:none --release 21` компилирует оба файла **без предупреждений**. Все исполнения и JUnit проходили внутри Docker с ограничениями памяти, CPU и PID. В первоначальном варианте были два предупреждения о неиспользованных ресурсах в try-with-resources; трассировка теперь использует имена обоих ресурсов, предупреждения устранены.

**16 из 16 настоящих JUnit-тестов прошли.** Включены независимые проверки:

- Дейкстра и Флойд сравниваются с отдельным Bellman–Ford на 12 случайных графах, девяти стартовых вершинах и двух порогах риска: всего 1 944 пары источник/назначение.
- Число инверсий mergesort сравнивается с квадратичным перебором на 40 массивах.
- Рюкзак проверяется полным перебором подмножеств для 30 вместимостей; скользящее окно — перебором всех интервалов для 20 бюджетов.
- Проверяются циклы зависимостей, точный баланс топлива, откаты частичной резервации, исчерпание слотов, состояние после завершения, пустые данные, повторяемость, CSV с кавычками и ошибками, порядок закрытия ресурсов и suppressed exceptions.
- На шести seed проверяется сохранение топлива и точное совпадение конечных статусов с replay журнала. Отдельно проверяется отмена уже запущенных миссий на лимите одного тика.

В основном прогоне выполнено **10 запусков, девять различных stdin**: пустой, `0 1`, `1 1`, `24 99`, `120 7`, `300 42`, `-4 3`, `abc`, `60 7 1`; `24 99` повторён. Вывод повтора совпал побайтно; пустой ввод совпал с `abc`. Все запуски завершились без timeout. Контрольные суммы:

| stdin | checksum |
| --- | --- |
| пустой / `abc` | 1040394504 |
| `0 1` | 2212306575 |
| `24 99` | 3310828445 |
| `120 7` | 929853924 |
| `300 42` | 2248243505 |
| `60 7 1` | 445314121 |

На машине разработки самый большой вход выполнился примерно за 1,2 секунды **вместе с запуском контейнера**. Это не измерение чистой JVM и не универсальный benchmark.

Две независимые безопасные AST-правки — индексный цикл → foreach и перестановка частей проверки диапазона в компактном конструкторе — сохранили stdout на пяти входах и прохождение всех тестов. Добавление/удаление метода также прошло полный round trip: число узлов вернулось к исходному, stdout совпал, JUnit успешен.

Две намеренные мутации скомпилировались и были пойманы:

| Мутация | Что произошло |
| --- | --- |
| В резервировании топлива `amount > available` → `amount >= available` | Падает тест точного баланса. Вывод пяти основных сценариев при этом не меняется: одних запусков main недостаточно для обнаружения ошибки |
| Расход на полезную нагрузку `mass * 3L` → `mass * 4L` | Падает тест формулы топлива; меняются четыре из пяти проверенных stdout |

Полные результаты, stderr javac, отчёты JUnit, stdout, хеши исходников и результаты каждой модификации: [results.json](results.json).

## JavaScope: найден и исправлен новый дефект

До исправления четыре компактных конструктора record (`Config`, `Edge`, `Route`, `Finished`) отсутствовали среди вызываемых блоков. Их внутренние проверки попадали в раздел членов класса и не имели правильного входа из конструктора. Парсер принимал исходник, поэтому успешный parse не выявлял ошибку визуального представления.

Исправлено формирование узлов, принадлежность тела конструктору, входные связи, название/бейдж, группировка и добавление инструкции в компактный конструктор. Обычный быстрый тест редактора теперь проверяет принадлежность, связь с условием и повторный разбор добавленной инструкции. Неявные присваивания record-компонент не разворачиваются; в интерфейсе есть явное предупреждение. Их семантика описана в [JLS 21 §8.10.4.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.10.4.2).

После исправления проект содержит **1 158 узлов и 1 139 рёбер**, из них 925 узлов относятся к монолиту. В Chrome с окном 1600×1000 обойдены **все 100 схем методов и конструкторов Main-файла**; пересечений прямоугольников блоков не найдено. Нулевое число пересечений не доказывает семантическую корректность рёбер и относится только к этому исходнику и конфигурации окна.

Через реальный интерфейс изменён порядок частей условия в `Config`. После AST-перегенерации всего большого файла настоящий javac успешен, 16 JUnit-тестов прошли, вывод совпал с оригиналом на заданном stdin (`matched_on_inputs`). Проверены переход из блока к нужной строке Java и выбор отдельной схемы тестового файла. Ошибок JavaScript не зарегистрировано.

Локальное доказательство: [browser.json](browser.json), [схема конструктора](compact-constructor.png), [Java/JUnit](java-and-junit.png), [схема Дейкстры](shortest-path.png).

## Что этот прогон не позволяет объявить готовым

**Big O на реальном коде остаётся слабым:** из 100 явных методов/конструкторов только четыре получили оценку, 96 вернули `unknown`. Например, линейный `linearEnergy` распознан, а бинарный поиск, mergesort, LIS, рюкзак, Дейкстра и Флойд — нет. Среди причин неподдержанные вызовы, рекурсия, исключения и слишком консервативная проверка изменений счётчиков/границ. Это отсутствие оценки, а не 96 доказанных ошибок алгоритмов. На учебных циклах распознавание заметно лучше, чем на составных реальных методах.

`try/catch/finally` и закрытие ресурсов всё ещё представлены структурно. В `cleanupTrace` Java правильно выполняет закрытие в обратном порядке, сохраняет два suppressed exceptions и выполняет finally после return из catch; схема весь маршрут не доказывает. Лямбды и switch expressions остаются непрозрачными для внутреннего потока. Record/type patterns разбираются и сохраняют компилируемость после AST-правок, но это не полный семантический анализ Java 21.

Длинная схема Дейкстры в общем масштабе плохо читается. Следующие полезные улучшения: корректный поток через finally, сворачивание веток и переходы между вызовами, затем расширение модели стоимости с проверяемыми правилами. Успешный JUnit сам по себе не подтверждает правильность визуальной схемы.
