# Проверка JavaScope на складской программе

Проверка начата 24 октября и завершена 25 октября 2026 года. Исходная опубликованная версия: `aef25b7`. Проверены предоставленные `Main.java` (1 192 строки, 63 объявленных метода) и `MainTest.java` (272 строки, 12 тестов). Оригиналы не менялись. Хеши, выводы Java, настоящие отчёты JUnit, результаты мутаций, сложности и геометрия браузера сохранены в [evidence.json](evidence.json).

**Оценка до исправлений: 3/10 для визуального редактора на этом файле. После: 6/10, рабочий MVP с существенными ограничениями семантики.** Это субъективная оценка по воспроизводимым дефектам, а не рассчитанная метрика качества. Парсер и исполнение Java были заметно надёжнее самой визуализации. Заявление «все блоки идеально работают» было бы неверным.

## Что действительно проверено

- JavaParser принял оба файла, нашёл все 63 метода Main. Настоящий JDK 21 с `javac -Xlint:all -proc:none` скомпилировал их без предупреждений. Все выполнения пользовательской Java проходили в Docker с действующими ограничениями ресурсов.
- Настоящий JUnit Platform 1.12.1 / Jupiter 5.12.1 выполнил **12 из 12 тестов успешно**, без заглушек API.
- Проверены восемь разных входов: пустой, `0 1`, `1 1`, `5 11`, `35 99`, `60 7`, `-4 3`, `abc`. `35 99` дополнительно запущен ещё дважды: stdout всех трёх запусков совпал. Пустой ввод совпал с `abc`.
- Подтвердились checksum: пустой ввод — `1874315167`, `0 1` — `199289198`, `35 99` — `2241818443`, `60 7` — `1192465059`.
- Через настоящие AST-операции независимо применены три изменения Клода: индексный цикл → foreach, расчёт веса while → for, тернарный оператор → if/else. Каждая версия скомпилирована, прошла 12 тестов и сохранила точный stdout на пяти входах: пустой, `0 1`, `5 11`, `35 99`, `60 7`.
- Две независимые мутации — GOLD 6% → 8% и частичная резервация для SILVER — скомпилировались, изменили результаты и были отвергнуты настоящим JUnit. Изменился вывод на пустом вводе, `35 99`, `60 7`; на `0 1` и `5 11` сохранился. Это полезная проверка тестов, но две мутации не доказывают их полноту.
- Добавление и последующее удаление неиспользуемого метода через AST сохранило выполнение на тех же пяти входах и прохождение 12 тестов. Оба невалидных примера Broken1/Broken2 отвергнуты с диагностикой.
- В Chrome 1600×1000 проверялись реальный DOM, пересечения прямоугольников блоков, выбор файлов/методов, редактирование и API-ответы. Успешное исполнение программы отдельно отрисованную схему не доказывает.

## Big O: была и опасная ошибка

На обязательных десяти примерах исходный анализатор распознал 6. После изменений распознаны все 10; результаты остаются **условными верхними границами**, не точными доказанными оценками:

| Метод | Оценка после исправлений |
| --- | --- |
| constantAccess | O(1) |
| linearSum | O(n) |
| halvingSteps | O(log n) |
| countInversions | O(n²) |
| gridWeightedSum | O(n × m), m — максимальная длина строки массива |
| countCommonSorted | O(n + m) |
| halvingSpanScore | O(n log n) |
| fixedWindowScore | O(n) |
| countAboveAverage | O(n) |
| totalDigitSum → digitSum | O(n × log V), V — максимальный модуль элемента; для Java int число цифр не больше 10 |

Главный контрпример не из готового набора:

```java
for (int i = n; i > 0; i /= 2)
    for (int j = 0; j < i; j++)
        x++;
```

Для положительного n число итераций тела равно `n + floor(n/2) + …`, то есть Θ(n). Старая версия сообщала **O(log² n)**: она подменяла величину счётчика числом его итераций и занижала стоимость. После исправления выдаёт **O(n log n)** — безопасную, но неточную верхнюю границу. Суммирование геометрически уменьшающихся объёмов пока не реализовано. Тест предотвращает возврат к занижению. Два указателя распознаются только при гарантированном продвижении во всех ветках; остановка, сброс или несколько потенциально переполняющихся шагов оставляют `unknown`.

## Что всё ещё мешает назвать редактор готовым

1. **Исключения и finally — главный оставшийся дефект семантики.** Например, `try { return 1; } finally { log(); }` обязан выполнить log перед возвратом, а структурный граф пока не представляет весь такой маршрут. Установка предупреждения исправляет честность интерфейса, но не сам граф. Резервации OrderProcessor с вложенными try/catch нельзя использовать как доказательство фактического порядка исполнения. Правила описаны в [JLS 21 §14.20.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-14.html#jls-14.20.2).
2. **Lambda, Stream API и switch expressions непрозрачны для внутреннего потока.** AST и компилируемый код сохраняются, но вложенная логика не разложена полностью. Нет связного межпроцедурного графа вызовов.
3. **Раскладка ещё слишком разреженная.** При читаемом масштабе видно начало метода, остальное требует прокрутки; «вписать» длинный метод уменьшает шрифт. Нужны сворачиваемые ветки и вложенные группы, переходы по вызовам, удобнее обзор и менее длинные обратные рёбра. Отсутствие пересечений блоков не означает отсутствие пересечений стрелок.
4. **Синтаксическая правка не гарантирует компиляцию.** Можно удалить нужную переменную, изменить сигнатуру без изменения вызывающего кода, добавить неверный return или получить недостижимую инструкцию. Run выявляет это настоящим javac/JUnit, но безопасного семантического рефакторинга пока нет.
5. **Сложность всего приложения не доказана.** Рекурсия, неподдержанные вызовы и побочные эффекты могут давать `unknown`; распознавание десяти учебных примеров не означает универсальный анализатор. Совпадение вывода на проверенных входах не доказывает эквивалентность программ.

Приоритет следующего этапа: корректный маршрут нормального/исключительного выхода через finally, затем внутренний поток switch expressions, затем сворачивание веток и навигация по вызовам. Добавление новых цветов блокам не решит эти проблемы.

## Проверки проекта

23 группы backend CI и одна группа frontend store/API прошли. Все пять браузерных сценариев прошли за 41 секунду, включая настоящее выполнение Java после case-правки, жизненный цикл метода и восстановление после невалидного исходника. Backend typecheck/build, frontend TypeScript/build и gateway smoke успешны. Lint не содержит ошибок; остаётся прежнее предупреждение `aiAnalyzer.ts` о лишнем экранировании и предупреждение сборки о крупном JS chunk (~707 КБ до gzip).

Быстрые проверки остались в CI, большой складской прогон и пять браузерных сценариев выполняются отдельно. В этом прогоне backend CI занял около 15 секунд, frontend store/API — около секунды. Время запуска Java включает контейнер и не сопоставимо с измерением чистого JVM у Клода; полноценный performance benchmark здесь не проводился.
